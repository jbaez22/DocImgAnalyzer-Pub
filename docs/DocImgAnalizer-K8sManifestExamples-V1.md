# DocImgAnalizer — Kubernetes Manifest Examples: Best Practice vs. Anti-Pattern (V1)

Reference examples for the Kubernetes manifest analyzer (`backend/app/services/k8s_manifest_analyzer.py`),
one bad/good pair per supported workload kind. Every score and finding list below was
generated by actually running the example through the real analyzer — not hand-computed —
so this doc stays true to the code's actual behavior.

## How the analyzer picks a workload apart

Before the rule-by-rule examples, two mechanical questions this doc exists partly to answer:

**1. How does it know if a manifest is a Pod, Deployment, or something else?**
It reads the top-level `kind:` field of each YAML document and checks it against a fixed
allow-list of 7 supported kinds. Any other kind (`Service`, `ConfigMap`, `Ingress`,
`Namespace`, etc.) is silently skipped — not an error, just ignored, unless *no* supported
kind is found anywhere in the manifest, in which case the whole request is rejected with
"No supported Kubernetes workload found." Once the kind is known, the analyzer locates the
actual container spec (the `PodSpec`) at a different path depending on kind:

| ----------- | -------------------------------------------------------- | -------------------------------- |
| Kind        | Where the app finds the PodSpec                          | Typical controller               |
| ----------- | -------------------------------------------------------- | -------------------------------- |
| Pod         | `spec` (the manifest's spec *is* the PodSpec)            | None — runs directly             |
| Deployment  | `spec.template.spec`                                     | ReplicaSet controller            |
| StatefulSet | `spec.template.spec`                                     | StatefulSet controller           |
| DaemonSet   | `spec.template.spec`                                     | DaemonSet controller             |
| Job         | `spec.template.spec`                                     | Job controller                   |
| ReplicaSet  | `spec.template.spec`                                     | Usually a Deployment             |
| CronJob     | `spec.jobTemplate.spec.template.spec` (one level deeper) | CronJob controller -> Job -> Pod |
| ----------- | -------------------------------------------------------- | -------------------------------- |

**2. Does every rule apply to every kind?** Mostly yes, with three deliberate,
kind-aware exceptions — the first two were added after the initial draft of this doc
surfaced them as false positives; the third was found the same way in a follow-up audit
using realistic, industry-standard manifests (not just synthetic bad/good pairs):

- **`DaemonSet` + K007 (`hostPath` volume)** — a node-level log/metrics collector
  *legitimately needs* a `hostPath` mount (e.g. `/var/log`) to do its job, so K007 is
  **downgraded from WARNING to INFO** (and its deduction from -15 to -5) specifically
  for `DaemonSet` workloads. It still fires — a `hostPath` mount is always worth a
  second look — but at a weight that reflects "verify this one actually needs it"
  rather than "this looks wrong." Every other kind still gets the full WARNING/-15.
- **`DaemonSet` + K006 (`hostNetwork`/`hostPID`/`hostIPC`)** — the same reasoning
  applies even more broadly here: `kube-proxy`, CNI plugins (Calico, Cilium, Flannel),
  and node-exporter-style metrics agents are all standard, widely-deployed DaemonSets
  that need host network/process visibility. A textbook-correct `node-exporter`
  DaemonSet scored only 65/100 before this fix, purely from K006 — clearly
  miscalibrated for a pattern that's essentially universal for that class of workload.
  K006 is **downgraded from ERROR to WARNING** (deduction -25 to -15) for `DaemonSet`
  only; every other kind still gets the full ERROR/-25.
- **`Job` / `CronJob` + K009 (no health probes)** — liveness/readiness probes are
  built for long-running, request-serving containers. A batch job that runs to
  completion and exits doesn't have a steady state a probe would check, so K009 is
  **skipped entirely for `Job` and `CronJob`** workloads — it no longer fires there at
  all. Every other kind (including `Pod`, which can itself be a one-off if
  hand-written without a Job wrapper) still gets it.

**Deliberately left alone: K002 (`privileged`) for `DaemonSet`.** CNI plugins like
Calico genuinely need `privileged: true` to manipulate host networking, and it's
tempting to treat that the same way as K006/K007 above — but `privileged` is a
meaningfully narrower, higher-risk elevation even within the DaemonSet population (most
DaemonSets — log collectors, metrics agents, config watchers — don't need it, unlike
`hostNetwork` which is close to universal for that class of workload). Downgrading it
would blunt the tool's actual value for the common real-world case of a DaemonSet that
sets `privileged: true` out of habit or copy-paste rather than genuine need. It stays at
full ERROR/-30 for every kind, including `DaemonSet`.

All four live in `backend/app/services/k8s_manifest_analyzer.py` — search for
`_PROBE_EXEMPT_KINDS` and `is_daemonset` to see the exact logic.

**K011-K013 (added after a gap review against an external scanner test-case spec) are
kind-agnostic** — they apply identically to every workload kind, with no exceptions:
hardcoded secrets, an auto-mounted ServiceAccount token, and a missing seccomp profile
are equally wrong regardless of what's running the container.

## Rule reference

| ---- | -------- | --------- | ------------------------------------------------------------------------ |
| Rule | Severity | Deduction | Check                                                                    |
| ---- | -------- | --------- | ------------------------------------------------------------------------ |
| K001 | ERROR    | -20       | Container image unpinned (no tag, or `:latest`)                          |
| K002 | ERROR    | -30       | `securityContext.privileged: true`                                       |
| K003 | ERROR    | -25       | No `runAsNonRoot: true` set at pod or container level                    |
| K004 | WARNING  | -15       | `allowPrivilegeEscalation` not explicitly `false`                        |
| K005 | WARNING  | -10       | Missing `resources.requests` and/or `resources.limits`                   |
| K006 | ERROR    | -25       | `hostNetwork`, `hostPID`, or `hostIPC: true` on the pod spec             |
| K007 | WARNING  | -15       | `hostPath` volume defined                                                |
| K008 | WARNING  | -10       | Capabilities not dropped (`drop: ["ALL"]` missing) or capabilities added |
| K009 | INFO     | -5        | No `livenessProbe`/`readinessProbe` (skipped for init containers)        |
| K010 | INFO     | -10       | `readOnlyRootFilesystem` not `true`                                      |
| K011 | ERROR    | -30       | Literal secret-like value in `env[].value` (not `valueFrom`)             |
| K012 | WARNING  | -10       | `automountServiceAccountToken` not explicitly `false`                    |
| K013 | WARNING  | -10       | No `seccompProfile.type: RuntimeDefault`/`Localhost` at pod or container |
| ---- | -------- | --------- | ------------------------------------------------------------------------ |

K011 only flags a literal `value:` matching a secret-like key name (`password`,
`token`, `secret`, `api_key`, `credential`, `private_key`, `access_key`, case-insensitive
substring match) — a `valueFrom.secretKeyRef`/`configMapKeyRef` reference is the correct
pattern and is never flagged. K013 uses the same container-then-pod fallback as K003.

## Pod

**Bad — score 0/100.** Findings: `K001` `K002` `K003` `K004` `K005` `K008` `K009` `K010` `K012` `K013`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: debug-pod
spec:
  containers:
    - name: shell
      image: busybox
      securityContext:
        privileged: true
```

**Good — score 100/100.** No findings.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: debug-pod
spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: shell
      image: busybox:1.36
      securityContext:
        privileged: false
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:
        requests:
          cpu: 50m
          memory: 32Mi
        limits:
          cpu: 100m
          memory: 64Mi
      livenessProbe:
        exec:
          command: ["true"]
```

## StatefulSet

**Bad — score 0/100.** Findings: `K001` `K003` `K004` `K005` `K008` `K009` `K010` `K011`
`K012` `K013`

Note `resources.requests`/`resources.limits` (K005) is about the **container's** CPU/memory,
not the `volumeClaimTemplates` storage size — those are unrelated fields, and this analyzer
doesn't check storage sizing at all.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres
          securityContext:
            allowPrivilegeEscalation: true
          env:
            - name: POSTGRES_PASSWORD
              value: "supersecret123"
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

**Good — score 100/100.** No findings. `readOnlyRootFilesystem: true` is still fine here —
Postgres's actual data directory is on the separate `data` PVC mount, not the root
filesystem, so it stays writable regardless.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 999
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: postgres
          image: postgres:16.4
          securityContext:
            privileged: false
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
            limits:
              cpu: "1"
              memory: 1Gi
          livenessProbe:
            exec:
              command: ["pg_isready", "-U", "postgres"]
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

## DaemonSet

**Bad — score 0/100.** Findings: `K001` `K002` `K003` `K004` `K005` `K007` `K008` `K009`
`K010` `K012` `K013`

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
spec:
  selector:
    matchLabels:
      app: log-collector
  template:
    metadata:
      labels:
        app: log-collector
    spec:
      containers:
        - name: collector
          image: fluent-bit
          securityContext:
            privileged: true
          volumeMounts:
            - name: varlog
              mountPath: /var/log
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
```

**Good — score 95/100, not 100.** Findings: `K007` only, at INFO severity — see the note
above. Everything fixable *is* fixed here; the remaining `hostPath` mount is the collector's
actual job (reading node logs), not an oversight, and the analyzer now reflects that by
only deducting -5 for it here instead of the usual -15.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
spec:
  selector:
    matchLabels:
      app: log-collector
  template:
    metadata:
      labels:
        app: log-collector
    spec:
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: collector
          image: fluent-bit:3.1.9
          securityContext:
            privileged: false
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 100m
              memory: 128Mi
          livenessProbe:
            exec:
              command: ["true"]
          volumeMounts:
            - name: varlog
              mountPath: /var/log
              readOnly: true
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
```

**Supplementary example — the K006 exception specifically.** The pair above only
exercises K007. `node-exporter` is the canonical real-world DaemonSet that needs
`hostNetwork`/`hostPID` instead of (or alongside) `hostPath`:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      hostNetwork: true
      hostPID: true
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.8.2
          securityContext:
            privileged: false
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 100m
              memory: 128Mi
          livenessProbe:
            httpGet:
              path: /
              port: 9100
          volumeMounts:
            - name: proc
              mountPath: /host/proc
              readOnly: true
            - name: sys
              mountPath: /host/sys
              readOnly: true
      volumes:
        - name: proc
          hostPath:
            path: /proc
        - name: sys
          hostPath:
            path: /sys
```

**Score: 75/100.** Findings: `K006` (WARNING, hostNetwork+hostPID) `K007` x2 (INFO, the
two hostPath mounts). Everything else about this manifest is fully hardened — this is
what a security-conscious, textbook-correct `node-exporter` deployment actually looks
like, and it still can't reach 100 because host-level visibility is structurally what
this workload is *for*. That's expected — these three findings exist to prompt a human
to confirm the DaemonSet's actual purpose justifies them, not to be "fixed" away.

`K013` (no `K009` — health probes are exempt for `Job`, see above)

```yaml
apiVersion: batch/v1
kind: Job

  name: db-migration
```

## CronJob

Note the PodSpec is nested one level deeper here (`spec.jobTemplate.spec.template.spec`) —
see the kind-detection table above.

**Bad — score 0/100.** Findings: `K001` `K002` `K003` `K004` `K005` `K008` `K010` `K012`
`K013` (no `K009` — health probes are exempt for `CronJob`, see above)

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool
              securityContext:
                privileged: true
```

**Good — score 100/100.** No findings. Same run-to-completion reasoning as `Job`.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"
  jobTemplate:

          restartPolicy: OnFailure

          securityContext:
            runAsNonRoot: true
            seccompProfile:
              type: RuntimeDefault
          containers:
            - name: backup
              image: backup-tool:2.3.0
              securityContext:
                privileged: false
                allowPrivilegeEscalation: false
                readOnlyRootFilesystem: true
                capabilities:
                  drop: ["ALL"]

                requests:
                  cpu: 100m
```
